# 통합설계서 작성·사용 방법

기능마다 `40_시스템설계/<구축 시스템>/<업무>/<기능>/설계서.md` 한 곳에서 설계의 목적과 구현 조건을 함께 관리한다. 업무가 여러 시스템을 거치면 목표업무에서 전체 흐름을 먼저 잡고, 각 기능의 입력·결과·책임 경계를 설계서에서 정한다.

## 두 독자의 읽는 순서

| 독자 | 시작점 | 다음에 확인할 내용 |
|---|---|---|
| 현업·기획·프로젝트 팀원 | 설계서의 목적, 범위, 정상·예외 흐름 | 규칙의 우선순위, 화면 메시지, 인수 사례의 기대 결과를 실제 업무와 대조한다. 합의가 필요한 질문에 담당과 결정을 남긴다. |
| 구현자·AI | 문서 머리말의 상태·개정·요구사항 ID | 승인된 개정의 규칙과 입출력을 읽고, 링크된 계약·데이터 정의를 연다. 인수 사례로 테스트를 만든 뒤 구현한다. 변경 결과에는 설계 ID·개정과 시험 ID를 남긴다. |

공통 원칙은 [공통 아키텍처](../30_공통아키텍처/), 시스템 간 교환 형식의 원본은 [인터페이스](../50_데이터와연계/03_인터페이스/), 시험 결과는 [검증](../60_검증/)에서 찾는다. 기능 폴더에는 기능 고유의 판단 규칙과 사용한 계약의 링크·버전을 둔다.

## 작성에서 인수까지

아래 상태와 절차는 프로젝트에서 채택할 수 있는 작성 방식이다. 승인 상태는 팀이 기존 검토 절차에서 해당 개정을 구현 기준으로 합의했다는 뜻이다.

1. [통합설계서 양식](통합설계서_양식.md)을 기능 폴더에 `설계서.md`로 복사한다. 요구사항, 설계, 계약, 인수 사례에 고유 ID를 부여한다. 기존 자료의 결정 번호가 있으면 근거에 함께 적는다.
2. 업무 담당자는 목적·경계·예외를, 개발자와 테스트 담당자는 입력값·실행 순서·기대값을 함께 검토한다. “적절히 처리” 같은 표현은 입력 조건, 결과 값, 상태 변화로 풀어 쓴다. 단위, 반올림, 경계값 포함 여부는 도메인에 해당할 때 명시한다.
3. 문서 상태는 `draft`(작성), `in_review`(검토), `approved`(합의한 구현 기준), `retired`(대체됨) 중 하나로 표시한다. 합의 근거와 개정을 남기고, 범위 안의 미결 질문은 영향받는 규칙·계약·인수 사례에 연결한다. 일부 기능만 먼저 확정하면 그 범위를 독립 설계로 나눈다.
4. AI에는 구현 대상 설계서와 참조한 계약·데이터 정의의 개정, 인수 사례를 함께 준다. 초안과 `EX-` 식별자는 시연 자료로 읽는다. 판정 조건이나 오류 처리에 충돌·공백이 있으면 관련 ID와 확인할 질문을 남긴다.
5. 요구가 바뀌면 같은 설계의 개정을 올리고 영향을 받는 규칙·계약·테스트를 함께 검토한다. 검증 결과에는 실제 실행한 설계 개정·코드 변경·테스트·차이를 연결한다.

## 파일의 역할

| 파일 | 내용 |
|---|---|
| `설계서.md` | 기본·상세설계를 합친 기능 원본. 머리말은 YAML로, 흐름·결정표·인수 조건은 Markdown으로 쓴다. |
| 인수 예시 JSON | 같은 입력의 기대 결과를 팀원이 읽고 자동화에서도 재사용한다. 기능이 외부로 제공하는 공식 계약은 인터페이스 원본을 참조한다. |
| 근거 시트·그림·위키 | 출처, 탭·단계, 채택한 요구·남은 질문을 기록한다. 업무 동작의 구현 근거는 합의된 설계 개정에서 찾는다. |
